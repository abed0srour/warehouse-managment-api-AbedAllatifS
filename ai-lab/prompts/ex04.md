## Prompt

>

### Decisions

**Followed the existing conventions.** `IClassFixture<CustomWebApplicationFactory>`,
`HttpClient` from `factory.CreateClient()`, FluentAssertions, `JsonDocument` for
response bodies, `IDisposable` cleanup for files written to `wwwroot/uploads/`,
and the same multipart form helper shape already used by `UploadProductImageTests`.

**Added one method to the shared fixture.** The prompt asks for assertions on
persisted side effects, but the existing integration tests only assert on HTTP
responses and had no route into the database. A `CreateDbContext()` accessor was
added to `CustomWebApplicationFactory`, opening a context over the same in-memory
database the application under test uses. The change is purely additive and all
24 pre-existing tests still pass unchanged.

**Asserted actual behaviour, not the behaviour the prompt described.** All three
routes were specified in terms the code does not implement (detailed below). The
tests pin down what the system really does and mark each divergence with a
`// GAP:` comment, rather than asserting a system that does not exist.

### Findings — all three routes differ from the prompt

**1. DELETE is a soft delete. Nothing is torn down and nothing cascades.**

The prompt asks to confirm the product and related data are "actually gone."
They are not. `ArchiveProductCommandHandler` calls `Product.Archive()`, which sets
`IsArchived = true` and persists; no row is ever removed. The row survives, the
table count is unchanged, and the product remains fully readable through
`GET /api/products/{id}` with a 200.

No cleanup cascades either:

- The uploaded image file outlives the "deleted" product, and nothing in the
  codebase will ever remove it — an unbounded leak of orphaned files.
- Related `Productimages` rows are untouched.
- The image endpoint checks only that a product *exists*, not whether it is
  archived, so images can still be attached to deleted products.

**2. The image endpoint performs no image processing.**

"Binary image stream upload/processing" overstates what is implemented. The
endpoint lowercases the filename extension, checks it against `.jpg/.jpeg/.png`,
and streams the raw bytes to `wwwroot/uploads/{id}{ext}`. There is no magic-byte
inspection, no decode, no re-encode, no resize. `MinioStorageService` exists in
the codebase and is not used by this route.

Consequences pinned by tests: a shell script named `payload.jpg` is accepted and
stored with a 200; the multipart `Content-Type` is never inspected, so only the
filename matters; and 64 KB of random bytes round-trip byte-for-byte unchanged,
confirming there is no processing step at all.

**3. The upload leaves no database trace.**

The prompt asks to confirm the image is "actually stored." It is stored on local
disk only. The schema contains a `Productimages` table with a foreign key to
`Products`, but nothing in `src/` ever inserts into it. The image is
undiscoverable by query — it can only be found by guessing the
`{productId}.{ext}` filename convention.

### Other defects found

**SupplierId is never linked on create.** `POST /api/products` copies
`SupplierName` as free text and never resolves it to a `Supplier` row, so
`SupplierId` stays null even when the named supplier exists. Products are
associated with their suppliers by denormalised string only.

**The Location header casing is inconsistent with the rest of the codebase.**
`CreatedAtAction` builds the URL from the `[controller]` route token, so the
header reads `/api/Products/{id}` with a capital P, while every hand-written URL
in the repo uses lowercase `/api/products`. Inbound routing is case-insensitive
so both work, but a client comparing the `Location` header literally would break.

**DELETE is idempotent, but silently so.** `Archive()` is unconditional, so a
repeat delete returns 204 rather than 404 or 409 — and it overwrites
`LastUpdatedAt` each time, meaning the archive timestamp reflects the most recent
call rather than when the product was actually archived.

`ai-lab/generated-code/ex04.cs` holds the code with no prose. It was compiled and
executed in an isolated project built only from that file plus `TestAuthHandler`
and `AssemblyInfo`: 57 passed, 0 failed.

The only mechanical change between the real source files and the flattened
artifact is that file-scoped namespaces were converted to block-scoped, since C#
permits only one file-scoped namespace declaration per file. Each file's `using`
directives are kept inside its own namespace block, which is deliberate —
hoisting them to the top makes `Product` and `Supplier` ambiguous between
`Warehouse.Domain` and `Warehouse.Infrastructure.Data.EfModels`.
